Search

iUsed when a search doesn't specify one.
iMax documents scored for semantic similarity per search, regardless of corpus size (also the ANN top-K, when active). Every BM25 match is always scored too -- this only bounds how many additional documents get sampled for a purely semantic match.
iOn Postgres with the pgvector extension installed, fills the semantic candidate pool from a real nearest-neighbor index instead of a bounded brute-force sample. Has no effect on SQLite/MySQL, or a Postgres server without the extension -- those always use the brute-force sample regardless of this setting. Uncheck to force the brute-force path for troubleshooting even when ANN is available.

Embeddings

iDependency-free feature hashing -- the default provider, not a trained model.
iWeight each enabled provider gets in the blended semantic score (0 = not used) -- weights are relative to each other, not absolute (1 and 1 weighs two providers equally, the same as 10 and 10 would). Switching which provider is active takes effect live, without a restart. Enabling a provider that wasn't already enabled changes the vector space entirely for it -- existing stored embeddings from a different provider are meaningless to compare against until every document is recomputed for it; see Embeddings to trigger that. Configure additional HTTP endpoints (any number, each independently enabled) on HTTP endpoints. Any search request may override these weights for itself via ?semantic=.
i0 embeds the body only, 1 the title only; in between, blends two separate Embed calls. Only takes effect for documents crawled, re-crawled, or explicitly recomputed afterward.

Link authority

iHow much link authority influences ranking (0 = no effect, 1 = ranking driven entirely by link authority).
iMinutes between automatic PageRank recomputations. A recompute also always runs right after a crawl finishes, since that's when the link graph actually changes.

Fuzzy matching

iWhen a query term has no matches at all, look it up against the index's vocabulary for a near-miss (within the edit distance below) and use that instead for scoring -- the displayed query is never rewritten, only what's used behind the scenes.
iHow many typos (insert/delete/substitute) a correction may be off by. A term that already matches something is never touched.
CrawlingFetch limits, rendering, link scope, version history

Crawler

iSeconds per page before giving up.
iSent with every fetch.
iUsed when a crawl doesn't specify one.
iShorter pages are skipped as thin content.
iMilliseconds to wait before each fetch after the first.
iKilobytes read from a page before truncating.
iNumber of past crawl jobs (with full per-page detail) kept before the oldest are deleted.
iHow many crawl jobs actually fetch pages at once; a burst of triggered jobs beyond this queues instead of running immediately. Raising or lowering it takes effect for the next job that starts, without a restart -- an already-running job keeps going until it finishes, so a lowered limit takes a little while to fully apply.
iHow a crawl fetches each page, unless it overrides this itself. Rendering a page in a real browser is much slower than a plain fetch (each page opens its own browser tab) and downloads that browser engine the first time it's ever used -- turn it on only for sites whose real content needs JavaScript to appear.
iHow far a crawl follows discovered links, unless it overrides this itself. "Seed's domain, including subdomains" follows e.g. blog.example.com and example.com from a seed of www.example.com, but not example.org. "Same domain, any subdomain, any top-level domain" is broader still -- from a seed of example.com it also follows example.org and www.example.de (the same domain name, any subdomain, under any TLD), but not other.com.
iWhen crawling a page, folds a leading "www." off its host before deciding its identity -- so www.example.com/x and example.com/x are always the same document (stored under the bare-domain URL), never crawled or indexed twice. Only affects future crawls; already-indexed duplicates from before this was enabled (or before it existed) are found and merged separately by content dedup, not by this setting. Turn off only for a site that genuinely serves different content at www. than at its bare domain.

Documents

iHow many versions of a document (current plus archived) are kept when a re-crawl changes its content. A document that's never changed always has exactly one version regardless of this setting -- it only bounds how much prior history a frequently-changing page accumulates. Lowering it prunes existing extra versions the next time that document is re-crawled, not immediately.

Content dedup

iFinds documents that are byte-identical or near-identical to another already-indexed document (a mirror, a copy under a different host, ...) and merges each group into one canonical document, so a search never lists the same content twice. A merge deletes the losing documents' own rows (their own link/version/embedding history is discarded, not migrated to the survivor) -- review the results on Content dedup, which also has a "recompute now" button.
iExact matches only byte-identical normalized text. Near-duplicate additionally matches within the SimHash threshold below.
iMax SimHash Hamming distance still considered a match (only used by the near-duplicate method).
iMinutes between automatic content-dedup passes. A recompute also always runs right after a crawl finishes, once enabled.
Content rulesBlocked and boosted terms and domains

Blocked

iOne per line; a document containing any of these is excluded from results entirely. Uses the same tokenization as search, so casing and punctuation don't matter.
iOne host or URL per line; a document served from any of these is excluded entirely.

Boosted

iOne "word factor" pair per line; a matching document's final score is multiplied by factor. A factor above 1 ranks higher, below 1 lower. Matching factors multiply together; zero or blank is ignored.
iOne "host factor" pair per line, same rules as boosted words.
